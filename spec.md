# AI Mystery Room — Product & Technical Specification

**Document type:** Single Source of Truth (SSOT)  
**Version:** 1.0.0  
**Status:** Ready for implementation  
**Project name:** AI Mystery Room  
**Architecture:** MERN Stack  
**AI Provider:** Google Gemini  
**Primary users:** Mystery enthusiasts, casual players, puzzle solvers  
**Primary objective:** Turn a user's short story or scenario into an interactive, AI-generated detective investigation.

---

# 1. Project Overview

## 1.1 Product Description

AI Mystery Room is an AI-powered mystery-solving web application where users provide a short scenario, story, or incident description. The application transforms that input into a fictional investigation containing suspects, clues, evidence, timelines, witness statements, and one predetermined culprit.

Players investigate the case by examining evidence such as:

- WhatsApp-style conversations.
- Photographs and visual clues.
- CCTV-style recordings, frames, and event timelines.
- Witness statements.
- Location and access records.
- Digital logs and other investigation documents.

After reviewing the evidence, the player selects the person they believe committed the crime or caused the incident.

The application evaluates the answer against the hidden solution and provides an explanation showing how the evidence supports the conclusion.

**Core principle:** The mystery must be logically solvable. Evidence must be internally consistent, and the culprit must be determined before the player starts investigating.

## 1.2 Problem Statement

Traditional mystery games often provide fixed stories with limited replayability. AI Mystery Room allows users to create personalized mysteries from their own ideas, resulting in a more dynamic and replayable investigation experience.

## 1.3 Product Goals

1. Generate a complete mystery from a user-provided scenario.
2. Create believable fictional suspects, motives, timelines, and evidence.
3. Provide an interactive investigation interface.
4. Ensure clues are consistent with the hidden solution.
5. Allow players to submit a culprit selection.
6. Explain correct and incorrect answers.
7. Support multiple independently generated mystery sessions.
8. Keep AI credentials and the hidden solution secure on the server.
9. Deliver a responsive experience on desktop, tablet, and mobile.

## 1.4 Out of Scope for Version 1

The initial version will not include:

- Multiplayer investigations.
- Real-time collaborative solving.
- Public mystery sharing or a community marketplace.
- User-generated video uploads.
- Real police, government, or criminal-record integrations.
- Live surveillance feeds.
- Payments or subscriptions.
- An unrestricted AI chat assistant.
- AI-generated voice acting or sound effects.
- A full administrative dashboard.

These can be considered for future releases.

# 2. Core User Journey

The application must support the following end-to-end workflow.

1. The user opens the landing page.
2. The user enters a scenario or short story.
3. The user selects the mystery difficulty and preferred case type.
4. The user submits the form.
5. The frontend displays a generation/loading screen.
6. The backend asks Gemini to generate the investigation.
7. The backend validates the generated case and checks its logical consistency.
8. If necessary, the backend retries generation or repairs the case.
9. The server stores the validated mystery in MongoDB.
10. The frontend navigates to the investigation room.
11. The player explores suspects, evidence, and the case timeline.
12. The player selects a suspect and submits a final accusation.
13. The backend evaluates the accusation against the stored solution.
14. The application displays the result and a spoiler-safe explanation.
15. The user can restart, return to the dashboard, or create another mystery.

**Important:** The culprit must not be disclosed to the frontend before the player submits their accusation or explicitly requests a solution reveal.

# 3. Functional Requirements

## 3.1 Mystery Creation

The creation page must provide the following fields.

| Field | Requirement |
|---|---|
| Scenario | Required; 30–2,000 characters |
| Difficulty | Easy, Medium, or Hard |
| Mystery type | Any, Theft, Murder, Disappearance, Cybercrime, or General Incident |
| Evidence quantity | Default 8; allowed range 6–12 |
| Case title | Generated by AI |
| Case description | Generated by AI |
| Culprit | Selected internally by AI and stored securely |
| Suspects | 3–5 suspects |
| Clues | 6–12 evidence items |
| Solution | Generated and stored privately |
| Estimated solving time | Generated or derived from difficulty |

The form must validate inputs before calling the API.

Additional requirements:

- Trim whitespace before submission.
- Reject empty scenarios.
- Enforce the scenario length limit on both client and server.
- Prevent duplicate submissions while generation is running.
- Show an understandable error if generation fails.
- Never expose Gemini API keys to the browser.
- Never allow a user to choose the culprit during creation.

## 3.2 Difficulty Levels

### Easy

- 3 suspects.
- Clear timeline and direct clues.
- At least two clues strongly support the correct conclusion.
- Minimal ambiguity.
- No essential clue depends on obscure inference.

### Medium

- 4 suspects.
- Several plausible motives.
- Contradictory or misleading statements.
- Requires connecting at least two pieces of evidence.
- Includes at least one red herring that can be resolved using other evidence.

### Hard

- 5 suspects.
- Interconnected evidence.
- More complex timeline reconstruction.
- Multiple plausible interpretations initially.
- Requires combining at least three pieces of evidence.

Difficulty must change the reasoning complexity, not the validity of the solution.

## 3.3 Case Introduction

Each mystery must contain:

- Case ID.
- Case title.
- Incident summary.
- Incident date and time within the fictional world.
- Incident location.
- Objective of the investigation.
- Difficulty.
- Suspect count.
- Evidence count.
- Optional estimated solving time.
- A short instruction explaining how to investigate.

Do not reveal the culprit or the decisive solution in the introduction.

## 3.4 Suspect Profiles

Every suspect must have:

- Unique suspect ID.
- Full fictional name.
- Age, if relevant.
- Occupation or relationship to the incident.
- Profile image or avatar.
- Short biography.
- Possible motive.
- Claimed whereabouts during the incident.
- Known relationships with other suspects.
- A statement about the incident.
- Potentially suspicious details.

The application must not automatically identify the culprit by highlighting one profile as correct.

Suspect descriptions should be comparable in detail. Avoid making the culprit obviously suspicious solely through wording or visual styling.

## 3.5 Evidence System

Evidence is the central feature of the application.

Each evidence item must have:

- Unique evidence ID.
- Evidence title.
- Evidence category.
- Short description.
- Detailed evidence content.
- Timestamp or time range when applicable.
- Source or origin.
- Related suspect IDs.
- Discovery status.
- Optional visual asset.
- Relevance to the investigation.

### Evidence categories

**A. WhatsApp-style conversations**

Display fictional message threads containing:

- Contact names.
- Message timestamps.
- Incoming and outgoing message styles.
- Message text.
- Optional read receipts.
- Optional edited or deleted message indicators, when relevant.

These are simulated conversations, not integrations with real WhatsApp accounts.

**B. Photographs**

Display AI-created fictional photographs or visual clues.

Examples include:

- An object found at the scene.
- A damaged lock.
- A misplaced item.
- A room or building.
- A fictional suspect-related object.

Each photograph must include a title, description, and any relevant observation.

**C. CCTV evidence**

Display a CCTV-style evidence viewer with:

- Camera name.
- Fictional location.
- Date and time.
- Recording start and end times.
- A visual frame or sequence of frames.
- An event timeline.
- A short AI-generated recording summary.
- Optional timestamped observations.

For Version 1, CCTV evidence may be represented by generated still images, timestamp overlays, and event sequences. Actual video generation is optional and must only be implemented when a compatible generation service is available.

Do not label a still image as a playable video.

**D. Witness statements**

Include witness identity, statement text, interview timestamp, and related suspects.

**E. Digital and physical records**

Examples include access logs, receipts, call logs, delivery records, inventory records, and location reports.

Every record must be fictional and created specifically for the mystery.

## 3.6 Evidence Interaction

Players must be able to:

- Open an evidence item.
- Read the full details.
- View images at a larger size.
- Filter evidence by category.
- Search evidence by title or content.
- View the associated timestamp.
- Navigate between evidence items.
- Mark evidence as reviewed.
- See which evidence items they have already reviewed.

Evidence review status is specific to the user's investigation session.

Reviewing evidence must not reveal whether it supports or contradicts the culprit unless that information is explicitly part of the evidence itself.

## 3.7 Investigation Timeline

Display a chronological timeline containing relevant events from the case.

Each event must include:

- Timestamp.
- Event description.
- Source evidence reference.
- Associated suspect IDs, when applicable.

Requirements:

- Sort events chronologically.
- Clearly distinguish confirmed events from disputed claims.
- Preserve contradictions when suspects provide conflicting statements.
- Allow players to open the evidence associated with an event.
- Avoid inventing events not supported by the generated case.

The timeline should be constructed from the case data and must not independently generate conflicting facts.

## 3.8 Accusation System

The player must be able to select one suspect and submit an accusation.

Requirements:

- The accusation screen lists all suspects.
- Exactly one suspect can be selected.
- The player can review their choice before submission.
- The user must confirm before making a final accusation.
- The backend compares the submitted suspect ID against the stored culprit ID.
- The player cannot change a submitted final answer.
- The result is persisted in MongoDB.

For Version 1, each case allows one final accusation per investigation session.

The response must include:

- Whether the answer is correct.
- The submitted suspect's name.
- The actual culprit's identity.
- A concise explanation.
- Supporting evidence references.
- The relevant reasoning chain.
- An explanation of significant red herrings.

The result page must only appear after a successful final submission.

## 3.9 Case History

Provide a basic dashboard containing previously created cases.

Each case card must display:

- Case title.
- Case creation date.
- Difficulty.
- Mystery type.
- Investigation status.
- Number of evidence items reviewed.
- Accusation status.

Users must be able to reopen an unfinished investigation and view completed results.

For Version 1, use anonymous session-based access unless authentication is explicitly added later. Persist a generated session identifier in browser storage and validate it on the server. Do not treat a browser-provided identifier alone as authorization to access arbitrary cases.

- Save asset references in MongoDB.
- If image generation is unavailable, render a clearly identified illustrative placeholder rather than claiming it is an AI-generated photograph.
- Represent CCTV with generated frames and timeline data unless actual video generation is supported.

Do not assume that every Gemini model can generate images or videos.

Create a media-provider interface so the implementation can add or replace a compatible media service without rewriting the mystery-generation logic.

# 6. System Architecture

## 6.1 Architecture Overview

The application follows a client-server architecture.

React frontend → Express REST API → Mystery service → Gemini provider → Validation service → MongoDB.

Media generation follows a separate path:

Mystery service → Media provider → Asset storage → MongoDB asset references.

The browser communicates only with the Express API. Gemini API keys, hidden solutions, provider configuration, and validation logic remain server-side.

# 7. Database Design

Use MongoDB with Mongoose.

## 7.1 Mystery Model

Collection: `mysteries`

```js
{
  title: String,
  scenario: String,
  description: String,

  difficulty: {
    type: String,
    enum: ["easy", "medium", "hard"]
  },

  mysteryType: {
    type: String,
    enum: [
      "any",
      "theft",
      "murder",
      "disappearance",
      "cybercrime",
      "general"
    ]
  },

  status: {
    type: String,
    enum: [
      "generating",
      "validating",
      "ready",
      "failed"
    ]
  },

  incident: {
    date: String,
    location: String,
    summary: String
  },

  suspects: [
    {
      suspectId: String,
      name: String,
      age: Number,
      occupation: String,
      biography: String,
      motive: String,
      alibi: String,
      statement: String,
      relationships: [String],
      avatarAssetId: String
    }
  ],

  evidence: [
    {
      evidenceId: String,
      title: String,
      category: String,
      description: String,
      content: Object,
      timestamp: String,
      source: String,
      relatedSuspectIds: [String],
      assetIds: [String]
    }
  ],

  timeline: [
    {
      eventId: String,
      timestamp: String,
      description: String,
      sourceEvidenceIds: [String],
      relatedSuspectIds: [String]
    }
  ],

  solution: {
    culpritSuspectId: String,
    motive: String,
    explanation: String,
    reasoningChain: [String],
    decisiveEvidenceIds: [String],
    redHerringExplanations: [String]
  },

  generation: {
    model: String,
    attempts: Number,
    validationStatus: String,
    createdAt: Date,
    completedAt: Date,
    failureCode: String
  },

  createdAt: Date,
  updatedAt: Date
}
```

### Important database rules

- `solution` is private server-side data.
- Never serialize the complete Mystery document directly to the client.
- Never return `culpritSuspectId` in pre-accusation API responses.
- Use a separate response serializer or DTO for public case data.
- Add appropriate indexes for case creation time, status, and ownership/session association.
- Store timestamps consistently in ISO 8601 format where possible.
- Validate all enum values and required fields.
- Avoid embedding large image or video binaries directly in MongoDB documents.

## 7.2 Investigation Model

Collection: `investigations`

```js
{
  mysteryId: ObjectId,
  sessionIdHash: String,

  reviewedEvidenceIds: [String],

  notes: [
    {
      noteId: String,
      content: String,
      createdAt: Date,
      updatedAt: Date
    }
  ],

  status: {
    type: String,
    enum: ["in_progress", "completed"]
  },

  accusation: {
    suspectId: String,
    isCorrect: Boolean,
    submittedAt: Date
  },

  result: {
    revealed: Boolean,
    revealedAt: Date
  },

  createdAt: Date,
  updatedAt: Date

```

Rules:

- A session can have multiple investigations.
- Each investigation references one mystery.
- Each investigation allows one final accusation.
- Enforce single submission using an atomic conditional database update.
- Do not accept `isCorrect` or the result from the frontend.
- Hash session identifiers before persistence.
- Return a public investigation DTO that does not contain internal ownership hashes or hidden solution data.

# 8. REST API Specification

Base URL during development:

`http://localhost:5000/api/v1`

All responses must use JSON.

## 8.1 Standard Response Format

Success:

```json
{
  "success": true,
  "data": {},
  "message": "Request completed successfully"
}
```

Failure:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please check your input",
    "details": []
  }
}
```

Do not return stack traces, API keys, database credentials, or internal prompts in production responses.

## 8.2 Endpoint List

### Health

`GET /health`

Returns application status and dependency availability without exposing secrets.

### Create mystery

`POST /mysteries`

Request:

```json
{
  "scenario": "A valuable painting disappears from a locked gallery.",
  "difficulty": "medium",
  "mysteryType": "theft",
  "evidenceCount": 8
}
```

The server must validate the input, create a mystery, invoke generation, validate the result, and persist the case.

Response:

```json
{
  "success": true,
  "data": {
    "mysteryId": "generated-id",
    "status": "ready",
    "title": "The Missing Masterpiece"
  }
}
```

If generation is asynchronous, return HTTP `202 Accepted` with a generation identifier and expose a status endpoint. Do not claim a case is ready before validation is complete.

### Get generation status

`GET /mysteries/:id/status`

Returns the generation status and a safe progress message.

### Get case

`GET /mysteries/:id`

Returns the case introduction, suspects, public evidence metadata, and timeline.

Must never return the hidden solution before accusation.

### Get evidence

`GET /mysteries/:id/evidence`

Returns a paginated or bounded list of evidence items.

Optional query parameters:

- `category`
- `search`
- `page`
- `limit`

### Get one evidence item

`GET /mysteries/:id/evidence/:evidenceId`

Returns the requested evidence item after validating session access.

### Get timeline

`GET /mysteries/:id/timeline`

Returns the case timeline and source evidence references.

### Create or resume investigation

`POST /investigations`

Request:

```json
{
  "mysteryId": "generated-id"
}
```

The backend creates an investigation or resumes the authorized unfinished investigation for that session and case.

### Get investigation

`GET /investigations/:id`

Returns investigation progress, reviewed evidence IDs, notes, and public status.

### Mark evidence reviewed

`PATCH /investigations/:id/evidence/:evidenceId`

Request:

```json
{
  "reviewed": true
}
```

The backend validates that the evidence belongs to the investigation's mystery.

### Update detective notes

`PATCH /investigations/:id/notes`

Request:

```json
{
  "notes": [
    {
      "noteId": "note-1",
      "content": "The witness timeline conflicts with the access log."
    }
  ]
}
```

The server must validate ownership and content length.

### Submit accusation

`POST /investigations/:id/accusation`

Request:

```json
{
  "suspectId": "suspect-2"
}
```

The backend must:

1. Authenticate or validate session ownership.
2. Validate the suspect ID.
3. Ensure the investigation is unfinished.
4. Compare the selected suspect against the stored culprit ID.
5. Atomically record the final accusation.
6. Mark the investigation completed.
7. Return the result and explanation.

Duplicate submissions must not overwrite the original accusation.

### Get results

`GET /investigations/:id/result`

Only return the solution if the investigation has a recorded final accusation or an explicitly authorized reveal action.

### List cases

`GET /mysteries?limit=20&page=1`

Returns only cases belonging to the current authorized session, unless a separate public-case feature is explicitly implemented.

### Delete a case

`DELETE /mysteries/:id`

Optional for Version 1. If implemented, verify ownership and remove associated investigation records and assets according to a defined deletion policy.

## 8.3 HTTP Status Codes

- `200 OK`: Successful retrieval or update.
- `201 Created`: Resource created.
- `202 Accepted`: Generation job accepted.
- `400 Bad Request`: Invalid request.
- `401 Unauthorized`: Missing or invalid session credentials.
- `403 Forbidden`: Access denied.
- `404 Not Found`: Resource not found.
- `409 Conflict`: Duplicate accusation or invalid state transition.
- `413 Payload Too Large`: Request exceeds configured limits.
- `422 Unprocessable Entity`: Valid JSON but invalid domain data.
- `429 Too Many Requests`: Rate limit exceeded.
- `502 Bad Gateway`: AI provider returned an invalid or failed response.
- `503 Service Unavailable`: AI provider unavailable.
- `500 Internal Server Error`: Unexpected server failure.

# 9. Gemini Integration Specification

## 9.1 AI Generation Strategy

Use a staged generation pipeline rather than asking Gemini to produce an unstructured story.

### Stage 1: Case blueprint

Generate:

- Incident description.
- Suspect roster.
- Actual culprit.
- Motive.
- Actual event timeline.
- Initial solution outline.

This blueprint is internal and must never be returned to the client.

### Stage 2: Evidence generation

Generate evidence based on the approved blueprint.

Every evidence item must reference existing suspect IDs and timeline events.

### Stage 3: Consistency validation

Check:

- The culprit exists in the suspect list.
- The number of suspects matches the difficulty.
- All evidence IDs are unique.
- All referenced suspect IDs exist.
- Timeline entries use valid timestamps.
- The culprit's actions are consistent with the timeline.
- The solution is supported by evidence.
- At least two independent clues support the correct accusation.
- The red herrings have reasonable explanations.
- The case is solvable without external knowledge.
- No essential clue contradicts another essential clue without an explicit explanation.

### Stage 4: Repair or retry

If validation fails:

1. Identify specific validation errors.
2. Send only the relevant structured case data and errors to the repair prompt.
3. Ask Gemini to repair the invalid portions without changing unrelated facts.
4. Revalidate the complete case.
5. Retry within a small configured limit, such as two repair attempts.
6. If validation still fails, mark generation as failed and provide a retry option.

Do not expose an invalid mystery to players.

## 9.2 Structured Output

Define a versioned JSON schema for the complete mystery.

The schema must validate all nested structures, enums, string lengths, array sizes, and cross-references.

Use Gemini's supported structured-output or JSON response mode when available, but always validate the returned data independently.

Never use `eval` to parse AI output.

Never trust generated content merely because it is valid JSON.

## 9.3 Mystery Generation Prompt

Use a maintained, versioned server-side prompt template equivalent to the following.

### System instruction

"You are a mystery-game scenario designer. Create an entirely fictional, logically consistent detective investigation for a game.

Follow the requested difficulty and mystery type. Establish the actual culprit, motive, event timeline, and complete solution before generating evidence.

Generate plausible suspects with distinct motives and alibis. Produce evidence that allows a careful player to identify exactly one culprit.

All evidence must be consistent with the established facts. Include red herrings that can be resolved using other evidence. Provide at least two independent clues supporting the correct conclusion.

Use unique IDs for all suspects, evidence items, and timeline events. All references must resolve to existing entities.

Do not rely on external facts or knowledge. Make the case solvable using only the supplied information.

Return only data conforming to the required JSON schema. Do not include markdown fences, commentary, or text outside the JSON object."

### User input template

"Create a mystery using the following parameters:

Scenario: {{scenario}}

Difficulty: {{difficulty}}

Mystery type: {{mysteryType}}

Evidence count: {{evidenceCount}}

Generate the case blueprint and evidence required by the supplied schema. Preserve the established facts throughout the case."

The backend must pass user input as data, not concatenate it into privileged system instructions. Treat all user-supplied text and generated text as untrusted content.

# 10. AI Safety and Content Rules

All cases must be clearly fictional.

Requirements:

- Do not use real private individuals as perpetrators in generated cases.
- Do not use real private conversations, accounts, or surveillance footage.
- Avoid defamatory accusations against identifiable real people.
- Label simulated chats and generated media as fictional evidence.
- Do not imply that generated evidence is authentic or suitable for real investigations.
- Do not generate content that encourages real-world violence or criminal activity.
- Apply safety checks to the scenario and generated output.
- Reject or safely transform disallowed scenarios.
- Prevent user-provided prompt injection from overriding system requirements.
- Do not allow the AI to execute generated code, database commands, or arbitrary tools.

For sensitive case types, use fictional characters and non-graphic descriptions.

The app is an entertainment and puzzle-solving product, not a real forensic or law-enforcement tool.

# 11. Authentication and Session Management

Version 1 uses anonymous sessions to minimize setup complexity.

Requirements:

- Create a cryptographically secure session identifier on the server.
- Deliver the session credential through a secure, appropriately configured cookie where feasible.
- Set `HttpOnly`, `Secure` in production, and appropriate `SameSite` attributes.
- Apply CSRF protections when required by the chosen cookie-based authentication design.
- Store a hash of the session identifier, not the raw credential.
- Verify session ownership for every private resource.
- Use a consistent expiration and cleanup policy.
- Avoid trusting arbitrary `sessionId`, `ownerId`, or `userId` values sent in request bodies.
- Never permit access to cases solely because the caller knows the MongoDB document ID.

If authentication is added in a future version, integrate a proper user account model and ownership checks without changing the core mystery domain model unnecessarily.

# 13. Performance and Reliability

Targets for the MVP:

- Landing page should render quickly on a typical broadband connection.
- Initial frontend bundle should be kept reasonably small.
- Database queries should use appropriate indexes.
- Evidence lists should be paginated or bounded.
- Images should use optimized formats and responsive dimensions.
- AI generation should use a configurable timeout.
- Generation must not block unrelated Express requests.
- Long-running generation should use a persisted job state if asynchronous processing is introduced.

For the first version, synchronous generation is acceptable only if the end-to-end request fits the configured timeout. Otherwise, use the asynchronous generation endpoint design defined above.

# 14. Error Handling

Implement a centralized Express error-handling middleware.

Handle the following scenarios:

| Scenario | Expected behavior |
|---|---|
| Empty scenario | Show field validation |
| Scenario too long | Reject with a clear message |
| Gemini quota exceeded | Show temporary service-unavailable message |
| Gemini timeout | Retry within configured limits or fail safely |
| Invalid Gemini JSON | Attempt bounded repair, then fail safely |
| Inconsistent evidence | Repair and revalidate before publishing |
| Mystery not found | Return 404 |
| Unauthorized case access | Return 401 or 403 consistently |
| Invalid evidence ID | Return 404 or validation error |
| Duplicate accusation | Return 409 without overwriting the answer |
| Database unavailable | Return a safe service error |
| Image generation unavailable | Use a clearly labeled fallback or omit optional media |
| Network failure | Display retry action where appropriate |

Frontend errors must be user-friendly. Development logs may contain additional diagnostics, but production responses must not expose internal details.

# 20. Final Product Principles

The following principles take precedence when implementation decisions arise:

**Truth over theatrics:** Every mystery must have a defensible, predetermined solution.

**Evidence over guessing:** The player must be able to identify the culprit using evidence in the case.

**Security over convenience:** Internal solution data and API credentials must never be exposed to the frontend.

**Consistency over volume:** A smaller, coherent case is preferable to a large case containing contradictions.

**Real functionality over mock functionality:** Production features must work through real APIs and persistence, with placeholders explicitly identified.

**Maintainability over shortcuts:** The application must remain understandable and extensible as new evidence types and AI capabilities are added.

**Fiction over real-world accusations:** All generated investigations and evidence must be clearly fictional.
